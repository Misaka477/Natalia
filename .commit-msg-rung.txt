fix(permission): the rung is a session write, and the web client can reach it

The user's report — "I switch the permission mode and only see a reload, the UI
does not change" — was two defects stacked, and the first one made the second
invisible.

1. THE RUNTIME FACE WAS UNREACHABLE. `apps/web/src/runtime-rpc.ts` (the web
   client's hand-maintained RPC table) had no `setSandboxRung` row, so
   `props.ctx.runtime.setSandboxRung?.(…)` answered `undefined`: the click never
   reached the daemon. No session mode change, no `context.instructions` record,
   nothing in the journal — measured by reading the deployed session's journal
   after two live switches (0 records). The only visible effect was the separate
   `updateConfig` the old code also ran, which is the reload notice the user saw.

2. THE SWITCH WAS NOT SESSION-SCOPED, so even a reachable write could not work.
   It patched `defaultAgentMode` + `confinement.mode` at scope "global" and
   re-read the config. `resolveConfig` merges defaults -> global -> project, so a
   workspace that pins those keys in its own `.natalia/config.json` outranked the
   write: the axes read back UNCHANGED (measured), `exec.permissionMode` never
   moved, and the model's per-turn `Permission mode:` line kept stating the old
   mode — the agent could not know its own rung either.

The fix:

- `SessionExecutionState.permissionModeOverride` — the approval axis's session
  choice, sibling of `sandboxModeOverride`. `config.reload` now writes
  `exec.permissionMode = override ?? deployment`, so a reload refreshes the
  deployment default underneath a session that never chose and leaves a session
  that did choose alone.
- `applySessionRung(ctx, sessionID, {approval, confinement})`: one act, both
  axes, one durable notice. `setSandboxRung` takes an optional `approval` (the
  selector sends it; a sandbox escalation does not) and answers with the axes.
  The notice names both halves, and the confirm-all axes ride the per-turn
  `<runtime_context source="environment">` block — `Permission mode: <x>` plus the
  confinement line — so the agent knows without the system prompt changing under
  the cached prefix (ADR D1). Contract, transport validation and refusal note
  updated with the field.
- The UI calls that one door and adopts the answer — never the config readback.
  When the runtime gives no answer the label stays put and the control says why
  (`permissionProblem`), because a control that looks alive while writing nothing
  is the exact failure above.
- The selector's rows no longer carry a `（当前）` suffix (the trigger already
  names the standing rung and the open row carries `data-active`), and the
  `DANGER` badge is gone from the top bar on the user's call — the confinement
  posture is still journal-derived in the view store for the audit trail.

packages/framework/client/test/sandbox-rung.test.ts

0 fail. New pins: the rung moves BOTH axes on the session and not the config
(the workspace pins both axes, so the old path is provably a no-op), the next
turn's environment block states `Permission mode: read_only`, a `reloadConfig`
does not stamp over the session's choice, the web client's RPC table names the
route the transport serves, and no option label carries `（当前）`.

Live on the deployed build (`E:\Natalia`, headless Edge over CDP): the trigger
moved `auto（工作区）` → `read` → `auto（系统）`; 0 reload notices, 0 `（当前）`, 0
danger badges; and the session's journal then held 2 `context.instructions
{kind:"sandbox_rung"}` records naming both axes (`…approval is now auto`) plus 2
`session.permission.mode` records — the durable half the next turn's environment
block is built from.
